# Processing analytics: d3-v1

EWSS-23 adds a standalone `run-analytics` command and `analytics-worker` Docker
target; matching has its own command and target. See the
[worker service runbook](worker-services.md) for separate settings and replica
verification. The legacy `run` command still runs both consumers together.
Matching retains `matching-worker-v1`.
Processing uses `analytics-processing-v1` on the same `ewaste.batch.events` topic,
starting at the earliest retained offset when that group has no committed offsets.
No new topic or Python database writer is introduced.
The Kafka group is created by the client; it is distinct from Azure's standard
[Event Hubs consumer groups](https://learn.microsoft.com/en-us/azure/event-hubs/apache-kafka-frequently-asked-questions).

```text
ReceiptVerified → RecyclingCompleted v1 (key = batch_id)
                            ↓ processing consumer
GET /api/v1/batches/{batch_id}/analytics-input?source_event_id={event_id}
                            ↓ validate frozen identity and SHA-256; evaluate d3-v1
POST /api/v1/batches/{batch_id}/analytics-results
                            ↓ Go transaction
result + anomalies + command + audit + COMPLETED + RequestCompleted outbox
                            ↓ Go relay / Python acknowledgement
RequestCompleted v1 on ewaste.batch.events / commit consumed offset + 1
```

Only `RecyclingCompleted` triggers analytics. `ReceiptVerified`, matching and completion
events are ignored by this consumer. Events use the existing approved schemas under
`contracts/matching/kafka`; processing uses `aggregate_version`, not `batch_version`.
Each partition remains ordered while API work retries. The two consumers have independent
offsets so old matching acknowledgements cannot hide retained processing events.

## Rules and identity

- Rule version is the Go contract's `d3-v1`. Unknown versions block rather than silently use another formula.
- Decimal strings only; at most two fractional digits. Normalise `12` to `12.00`; reject excess precision rather than rounding.
- Fixed flag order: `CATEGORY_MISMATCH`, `COUNT_MISMATCH`, `WEIGHT_MISMATCH`, `MISSING_OUTCOME`, `UNALLOCATED_WEIGHT`.
- Compare donor declaration with facility receipt, not collector handoff count. Signed deltas are received minus declared. Any `0.01` kg difference is flagged.
- `diverted_kg = reused_kg + recycled_kg`; `unknown_kg = actual_weight_kg - reused_kg - recycled_kg - disposed_kg`.
- All three amounts absent: known amounts and diverted are null; unknown is the entire received weight; quality `MISSING`. All three present with a remainder: `PARTIAL`. Fully allocated: `COMPLETE`.
- Zero amounts are supplied data, not missing data. Negative, mixed-null, excess allocation and invalid receipt values are rejected. Evidence remains optional; no missing-evidence anomaly or CO2 estimate.
- Valid `MISSING` and `PARTIAL` results may complete the batch through Go.

Hash the exact UTF-8 `input_canonical_json` returned by Go. Validate all frozen fields
against the Kafka source, including receipt/treatment IDs and versions, source version,
rule, batch and correlation. Recompute totals and reject inconsistent frozen totals.
The worker returns those identifiers, input hash, metrics and flags using the existing
Go DTO. Correlation is preserved, including the contract's 128-character limit.

`analytics_run_id` is UUIDv5 over source event, rule version and input hash. The command
key is `analytics-v1:<source_event_id>`; `If-Match-Version` remains the original source
aggregate version, including replay after completion. An uncertain/lost response retries
the same POST. Only a matching durable completion response permits offset advancement.
Go enforces source/result uniqueness and atomic completion; Python never publishes
`RequestCompleted` directly.

## Configuration and release order

1. Apply the existing processing migrations through the master Liquibase changelog.
2. Provision existing Event Hubs, API and worker resources. Terraform and CD select the environment secret `EWASTE_AUTH_ANALYTICS_SERVICE_TOKEN`, falling back to legacy `ANALYTICS_SERVICE_TOKEN` only when the former is absent. Both use the same value, separate from `MATCHER_SIGNING_SECRET`, with at least 32 characters. The workflows reject a missing token instead of deploying a checked-in development placeholder.
3. Deploy the Go API supporting `processing-v1`; the existing authenticated CD preparation probe must pass before worker rollout.
4. Deploy the immutable Python image. CD and Terraform both retain `ANALYTICS_ENABLED=true`, `ANALYTICS_GROUP_ID=analytics-processing-v1`, `ANALYTICS_FACADE_URL`, and the `analytics-service-token` secret reference. The API uses `EWASTE_AUTH_ANALYTICS_SERVICE_TOKEN`.
5. Confirm both consumers are polling and `/readyz` succeeds. No business event is generated by the deployment probe.

In legacy combined mode, the processing consumer reuses the matching Kafka TLS/SASL, HTTP timeout, maximum
record/response sizes, worker count and retry settings. Matching-only installations
without an analytics token remain supported; an explicitly enabled worker without
valid configuration fails startup. Both consumers must be healthy for container readiness.
An unexpected consumer exit stops the other consumer and fails the process.

## Failure recovery

`delivery_paused`, `processing_step`, `consumer_lag`, readiness and offset observations
reuse the existing structured telemetry. They retain batch/event/correlation/run IDs,
consumer group, stage, attempt count, duration and bounded error codes. Raw payloads,
tokens, API bodies and exception strings are not logged.

| Signal                                                 | Action                                                                                                                                        |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `ANALYTICS_AUTH_FAILED`                                | Restore the shared service credential and restart the revision if its secret changed.                                                         |
| `ANALYTICS_FACADE_UNAVAILABLE`                         | Restore API/database availability; the same request retries with capped backoff and Retry-After.                                              |
| `ANALYTICS_FACADE_REJECTED`                            | Inspect the retained event, Go command/result and API logs for state/version/validation conflicts.                                            |
| Input hash/identity/total mismatch or unsupported rule | Repair the producer/façade/configuration or deploy the supported rule. Do not fabricate a completion or skip offsets to make readiness green. |
| Offset commit failure after completion                 | Let redelivery replay the saved Go result. Do not delete command or result rows.                                                              |

No approved processing DLQ exists. Invalid processing records block that partition and
readiness, with observable retries. This deliberately avoids silently discarding business
events or repurposing the matching quarantine contract. Recovery preserves source identity.
Events already outside Kafka retention need a separately reviewed replay procedure.

## Repeatable verification and evidence

Run from the repository root:

```sh
bash scripts/test-matcher.sh
```

The script builds disposable Go/MySQL/Kafka/Redis services, migrates a clean database,
repeats migrations, runs Go tests and all Python tests with an enforced **85% minimum**,
then removes only its own containers and volumes. It uses no Azure credentials or ports.
Test accounts receive temporary passwords inside that database only; login responses
and credentials are excluded from journey evidence.

| Task                           | Executable evidence                                                                                                                                                                                                              |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EWCSB-171 worker               | `test_analytics.py`, `test_analytics_worker.py`; 26 versioned golden cases in `tests/fixtures/analytics-d3-v1.json`                                                                                                              |
| EWCSB-172 delivery/persistence | Real Kafka redelivery/restart; lost successful HTTP response; forced failure at final completion outbox insertion proves result/command/audit/state rollback; exactly one durable completion after recovery                      |
| EWCSB-178 journeys             | Donor create/submit → match → claim → assign → handoff → receipt → treatment → analytics; clean, discrepant/partial, missing and all-zero cases; SQL compared with processing detail, auditor anomalies/timeline and impact APIs |

Golden receipt-only examples supply a fully allocated treatment for end-to-end evaluator
tests so receipt mismatches are not confused with missing-outcome flags. Pure fixtures are
fixed and deterministic. Journey timestamps/UUIDs are generated by the API; comparisons
use the frozen resulting source, and the evidence index records those exact identities.

Each run retains `artifacts/matcher/<run>/`:

- `base-commit.txt`, `test-inputs.sha256`, `contracts.txt`: release/source identity.
- `migrations.log`, `migrations-repeat.log`, `go-tests.log`, `tests.log`, `junit.xml`, `coverage.xml`.
- `analytics/index.json`: task, batch, correlation and source-event index with reconciled totals.
- `analytics/queries.sql`, `sql-results.jsonl`, per-batch rows, `api-journeys.jsonl`, `analytics-facade.jsonl`, `kafka.json`, `rollback.json`, `recovery.jsonl`.
- `services.log`, `cleanup.log`, `result.txt`.

The four journey batches have 46.50 kg received, 20.00 kg diverted, 2.00 kg disposed
and 24.50 kg unknown. Missing amounts remain null per batch; aggregate sums do not turn
missing data into claimed diversion. The denominator for this evidence is four distinct
completed fixture batches, not anomaly-row count.

**UI verification remains pending:** the current frontend processing and impact tabs are
placeholders. This task verifies their backing API data, not a rendered screen. The current
impact endpoint returns result items and a count; this evidence reconciles totals from those
items and does not claim a server-side filtered aggregate endpoint exists.

The journey test also guards a predecessor defect: claim/assignment event times must be
microsecond-aligned before MySQL writes, otherwise rounding can quarantine an earlier
event and prevent the processing event from reaching Kafka. Existing quarantined production
rows are not rewritten by this change.
